# 氏名・フリガナの判断と回帰検証

氏名・読みの判定を変更・検証する開発者向けの文書です。
補正履歴の操作は [利用ガイド](../users/README.md#補正履歴) を参照してください。
以下のコマンドはリポジトリのルートから実行します。

処理バージョン29では、氏名の表記・姓名の境界・読みの根拠を分けて判断する。
抽出時に保存済みのOCRは変更しない。OCR段階で氏名を再認識した場合や、読みの検証で
ローマ字を補正した場合は、初回の文字列と判断根拠を記録する。

以前は複数の補正が別々に氏名・読みを書き換えており、候補の採用条件や空白の扱いが
一致していなかった。現在は会社・部署・役職・資格の除外とOCR根拠を共通化し、
氏名の決定→読みの決定→確認済みの訂正の順で処理する。連絡先は照合前にOCRで裏付ける。
候補を全て集めてから比較し、同じ強さの異なる人物候補が残った場合は選ばない。

## 処理の担当

| ファイル | 担当 |
| --- | --- |
| `api/src/services/name_evidence.py` | OCR本文・座標・ルビ・氏名に対応するローマ字の根拠を調べる。読みの矛盾も判定する。 |
| `api/src/services/person_identity.py` | 人名の印刷を確認し、会社・部署・ロゴを除外する。姓名の順序と区切りを整理する。 |
| `api/src/services/kana_reading.py` | 共通の根拠とデジタル庁の氏名漢字カナ突合モデルから、読みを一度選ぶ。必要な場合は姓名の境界も検証する。 |
| `api/src/services/feedback.py` | 共通の根拠を尊重し、利用者が確認した読みの補正を適用する。 |
| `api/src/services/extractor.py` | 上記の処理を順に実行し、元応答・自動採用値・補正後の値・判断理由を記録する。 |

## 氏名の規則

- 氏名の文字列は、OCRの独立した行・ブロック・近接した文字の組み合わせで確認する。
  会社名の一部分に含まれるだけの文字列は、人名の根拠にしない。
- 日本語氏名とローマ字の姓名が同じ行・ブロックにある場合は、行全体の形式を確認して
  検証用に分離する。保存したOCR本文・領域は変更しない。会社名・役職や、同じ行で
  法人格に隣接する領域は引き続き除外する。読みの採用は別途、従来の根拠で検証する。
- 漢字の姓・名の上に小さなローマ字がある場合は、同じ面・同じ行・列の重なりから対応を確認する。
  メールのアカウントにもローマ字の一致を求める。OCRが漢字を短く読み落としたり店舗名として
  読み違えたりした場合は、文字枠に高さの10%・20%の余白を足して一度だけ再認識する。
  2つの結果が一致し、双方のスコアが0.9以上の人名らしい漢字である場合だけ採用する。
  初回の文字列・再認識の枠・結果・スコアは領域の `_recognition_retry` に残す。
  ローマ字から印刷されていない漢字を生成することはしない。
- OCR座標は、分かれた文字を印刷順に結合するために使う。
  役職と氏名が同じ領域に含まれ、既知の役職の直後に空白がある場合は、役職を除いて
  人名の断片を結合する。氏名の先頭文字だけを理由に役職を切り落とさない。
  氏名の印刷を確認した後、役職欄が「既知の役職＋氏名」または逆順なら役職だけにする。
  役職欄に氏名の先頭部分だけが残った場合も、同じ組み合わせがOCRの行・領域にあるときに除く。
  文字の大きさは各面の候補文字に対する比率で判定し、固定の40pxを下限にしない。
  姓名間に広い空白があっても同じ面・同じ行・文字の大きさに対する距離を確認して結合する。
  既に姓・名の2つに分かれた値を、OCRの領域が2つという理由だけで変更しない。
  例えば「夢野 正」／「宗」という領域から「夢野光 宗」へ変更しない。
- 4文字の氏名を一律に2文字ずつに分割しない。
  空白で分かれた文字列と姓だけのメールアカウントを使う場合、長音の「う」の省略も
  姓・氏名全体のモデル候補との一致から確認する。メールだけで境界や名を生成しない。
  「秦 嘉一郎」「長谷川 亮」のような境界も検証する。
- 読みを使って境界を復元する場合は、姓の読みと氏名全体のモデル候補が対応することを確認する。
- 再スキャンでは、空白を除いた氏名とメールアドレスまたは携帯番号が一致し、
  氏名の印刷も確認できた場合だけ、既存の姓名の区切りを利用する。
- OCRが名を読み落とした再スキャンでは、会社名などの誤抽出を除外した後、
  姓が独立した行または領域に印刷され、メールアドレスと携帯番号の両方が既存値と一致する場合に限り、
  既存の氏名・フリガナを維持する。連絡先は今回のOCRに根拠がある値だけで照合する。
  異なる人物名を印刷から確認できる場合、この維持処理は適用しない。
  名の文字は新しく推測しない。既存のふりがなが姓名2つに分かれた有効な値なら、その値を維持し、
  読みモデルへの問い合わせを省く。空欄・区切りなし・無効な既存値は「読みを保持済み」と扱わず、
  引き継いだ氏名をbzcard-kanaで推測する。読みモデル停止時は空欄を維持し、その理由を記録する。
  氏名と読みそれぞれの判断理由を解析履歴に記録する。
- 根拠のない境界は作らず、文字間の不要な空白を除いた氏名と未確定の理由を残す。
- LLMが会社名を氏名にした場合、ルビ・ローマ字に加えて一意なOCR氏名候補からも復元する。
  一つの領域に姓名が印刷されている場合も対象にする。複数の人物候補が残る場合は先頭を選ばず、
  会社名の誤抽出を指摘して一度だけ再推論する。再推論でも確定できなければ未確定とする。

会社名は、法人格を含むLLMの抽出値がOCRの会社名行の末尾と一致する場合、その値を維持する。
ロゴを数字として読み取ったOCR行全体で一律に上書きしない。会社名に元々含まれる数字は削除しない。
一致した部分の単語間の空白はOCRに合わせる。日本語社名の途中にLLMが追加した空白を除き、
OCRに実際にある単語間の空白と、法人格の前後に入れる標準の空白は維持する。

住所の先頭が都道府県名から1文字だけ欠けた形で、市区郡と数字もある場合は、
OCR領域を高さの30%・40%だけ広げて再認識する。双方がスコア0.9以上で、
先頭1文字を回復した同じ住所を読み取った場合だけ採用する。都道府県の一覧は再認識の
対象を選ぶために使い、文字を推測で追加しない。初回の文字列と再認識の根拠は
`_recognition_retry` に記録し、不一致・低スコア・例外の場合は初回の結果を維持する。

役職は `roles.py` の一覧を氏名の除外・部署からの分離・抽出で共有する。
「グループ長」も役職として扱う。LLMがOCRにない役職を返して除外された場合や、
役職を空欄にした場合、OCRの独立した行にある既知の役職が1種類だけなら復元する。
複数の異なる役職がある場合は選ばず、既にOCRに裏付けられた役職があれば維持する。
「部長室」などの一部分から役職を生成しない。

## 読みの規則

1. 氏名に対応する印刷されたカナ・ルビを優先する。
2. 氏名とメールアドレス、または氏名の読みモデルで対応を確認したローマ字を使う。
   姓名の順序や長音は既存の根拠・読みモデルの候補と照合する。
   メールの最後の単語を無条件に姓としない。姓の候補が誤っていても、
   氏名全体の候補から分離した名の読みが対応すれば、ローマ字の順序を確認できる。
   無関係な英語の社名・スローガンは読みの根拠にしない。
   メールのOCRが読み違いでも、印刷された日本語氏名とローマ字の姓名について、
   姓の候補と氏名全体の候補から分けた名の読みが双方一致すれば採用する。裏面のローマ字も対象にする。
   姓だけの一致では採用しない。空白なしの氏名は姓の長さ1～4文字を全て検証し、
   区切りと読みが一意になった場合だけ姓名の空白とふりがなを同時に復元する。
   候補が複数・モデル停止・漢字氏名の印刷が未確認の場合は、この方法で復元しない。
   根拠は `verification: family_and_full_name_model_match` と `roman_pairs` に記録し、
   その読みも過去の訂正履歴より優先する。
   日本語氏名の直後にローマ字の姓名がある場合は、メールのアカウントが1要素でも、
   その要素がローマ字の片方と完全一致すれば関連を確認する。メールだけで姓名の順序は決めない。
   ローマ字の片方が変換不能で、もう片方が姓のモデル候補と一致する場合は、名だけの読み候補を調べる。
   変換不能の文字列から1文字の置換で一意の候補に一致する場合だけ、検証用に補正して採用する。
   変換可能な綴りは補正しない。複数候補・対応不明・モデル停止の場合は、無関係な漢字読みで
   上書きせず未確定とする。採用した元の綴り・補正候補・読みは解析履歴に記録する。
   この照合で確認した読みも、過去の訂正履歴より優先する。
3. 印刷上の読みがない場合、同じ利用者が確認した同一人物の補正を優先する。
4. 同一人物の再スキャンで、既存の読みが姓と氏名全体のモデル候補に含まれる場合は維持する。
   別人の読みやモデルに裏付けられない既存値は、この規則では流用しない。
5. それ以外は読みモデルの候補から推論する。モデル停止や候補不足の場合は、
   同一人物の有効な既存読みを維持する。既存値がなければ有効な形式のLLM推測値を
   代替として残し、代替の理由を記録する。別人の既存値は利用しない。

印刷された複数の読みが矛盾する場合は、最初の値を勝手に選ばずフリガナを未確定にする。
モデルの「ゆめの／さと」のような順位付き候補は、印刷上の矛盾とは別に扱う。
判断は解析履歴の `model_json` 内の `identity` と `kana` に記録する。
`selected` は実際の採用値と一致させる。

漢字だけから本人の読みを完全に確定することはできない。
「月野 祥介」は新規登録ならモデルの上位候補「つきの ひろあき」が推論されるが、
既存の同一人物を再スキャンするときは、候補にも含まれる「つきの しょうすけ」を維持する。

## 回帰検証

テストには架空の氏名・連絡先と合成画像を使う。個人別の正解表は本番処理から参照しない。
空白・姓名逆順・会社名や役職の混入、印刷上の矛盾、モデル停止、既存読みの維持を検証する。
座標を使う検証では、縮尺や文字間隔を変え、別の行・面の文字を結合しないことも確認する。
実際の名刺の氏名・連絡先・OCR全文・解析履歴をテストや開発文書に追加しない。

APIの全テスト（本番データをマウントしない）:

```sh
docker build -t bzcard-api:distribution-test api
docker build -f api/Dockerfile.test -t bzcard-api:test api
docker run --rm --network none -v "$PWD/api:/app:ro" -w /app bzcard-api:test \
  python -m unittest discover -p 'test_*.py'
```

保存済みのOCRとLLM応答を使い、現在の処理で全解析履歴を再生する:

```sh
docker compose -f docker-compose.develop.yml run --rm -T --no-deps -v "$PWD/api:/app:ro" api \
  python replay_person_identity.py --check --fresh
```

これは読み取りのみの検証で、OCR・LLMの再実行や名刺の更新は行わない。
読みモデルには問い合わせる。`--check` は再スキャン相当の氏名・読みが現在の登録値と
違う場合に失敗する。`--fresh` は既存値を利用しない推論結果も比較用に出力する。
現在値との違いは必ずしも不具合とは限らないため、変更内容と根拠を確認する。
