# 人物一覧の取得

人物一覧のDB・API・ページ取得を変更する開発者向けの文書です。
画面での一覧・検索操作は [利用ガイド](../users/README.md#一覧検索編集) を参照してください。

WebUIは最初に50人を取得し、一覧の下端に近づくと次の50人を取得する。
詳細と画像は表示する人物・名刺に応じて取得する。検索は取得済みのページに限らず、
その利用者の全登録名刺を対象にする。

## DBに保存する情報

`contact_summaries` に一覧の要約、`contact_members` に所属名刺、
`contact_identifiers` に正規化したメールアドレス・携帯番号を保存する。
`contact_search` には検索用に正規化した項目と表裏のOCRテキストを保存する。
利用者IDを含めて保存し、人物の判定・検索・取得を利用者ごとに行う。

メールアドレスまたは携帯番号が一致する名刺を同じ人物にまとめる。
名刺AとBのメール、BとCの携帯が一致すればA・B・Cをまとめる。
氏名や会社名だけの一致ではまとめない。状態の絞り込みでは、従来どおり
その状態の名刺だけで人物を判定するため、接続する名刺が隠れると人物が分かれる場合がある。

名刺の追加・削除・項目編集・OCR・画像変更はDBトリガーで変更対象を記録し、
保存するトランザクション内で関連する人物を更新する。識別情報の変更や橋渡しする
名刺の削除による統合・分割も反映する。通常の一覧取得では全名刺を再分類しない。
直接SQLiteへ書き込む取り込み処理の変更も、次のAPIのDBアクセスで反映する。

スキーマ移行バージョン2で、既存名刺から初回の要約を作る。名刺や画像は削除しない。
この初回だけは登録済みの全名刺を処理するため、件数に応じてAPIの起動に時間がかかる。
再起動時は作成し直さない。

## API

`GET /api/contacts?limit=50` は次の情報を返す。

| 項目 | 意味 |
| --- | --- |
| `items` | 人物の要約。各人物の `revision` は所属名刺の変更を表す |
| `next_cursor` | 次ページの取得位置。最後のページでは `null` |
| `revision` | 利用者の一覧全体の更新世代 |
| `has_in_progress` | 未取得のページを含む、その利用者の処理中名刺の有無 |

`limit` は1〜200。`q` と `status` は従来どおり使える。
続きは同じ検索・絞り込み条件で `cursor=<next_cursor>` を指定する。
カーソルは利用者・検索条件・状態・更新世代に紐付く。別の条件で使うと400、
途中で名刺が変更されると409を返す。WebUIは409の場合、既に取得した人数まで
先頭から再取得し、選択中の名刺と未保存の編集を維持する。

`known_revision=<revision>` を指定して先頭ページを確認し、変更がなければ
`unchanged: true` と空の `items` を返す。WebUIはこの場合、表示中の一覧を維持する。
ページ取得に失敗した場合は「続きを再試行」で再取得できる。

`limit` を省略した既存のAPI呼び出しは全件を返す。
LINE連携で使うページ分割なしの呼び出しも継続する。
人物の詳細は `GET /api/contacts/{id}` で所属名刺だけを取得する。
所属するどの名刺のIDでも、その人物を取得できる。

検索は既存の部分一致・表記の正規化・順位を維持する。複数の検索語が同じ人物の
異なる名刺に分かれていても一致する。検索時には全件の正規化済みテキストを評価するため、
検索時間は件数に応じて増える。検索なしの一覧はDBインデックスで対象ページだけを取得する。

## 検証

API回帰テストで統合・分割、利用者の分離、過去の名刺の検索、初回移行、
取得中の更新、カーソル検証、ロールバックを確認する。
ブラウザ回帰テストでは架空の145人を使い、50人ずつの取得、スクロール位置の維持、
未取得の人物の検索、409からの復旧、取得失敗時の再試行、未保存の編集の保持を確認する。
